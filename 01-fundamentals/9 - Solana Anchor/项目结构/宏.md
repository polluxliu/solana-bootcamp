# 宏

Anchor 框架使用 Rust 宏来减少样板代码，并简化编写 Solana 程序所需的常见安全检查。

在 Anchor 程序中，主要的宏包括：

- **declare_id**：指定程序的链上地址，即，program ID，默认情况下，program ID 是在 `/target/deploy/your_program_name.json` 路径下生成的密钥对的公钥。
    
    ```bash
    anchor keys sync
    ```
    
    运行该命令，Anchor 会将本地生成的程序密钥对（即 `/target/deploy/your_program_name.json` 文件中的公钥）同步给项目的 `declare_id!` 宏的值，确保两者一致。
    
- **#[program]**：用于标注包含所有指令处理器的模块。在 Solana 程序中，**instruction handlers**（指令处理器）指的是处理来自客户端或其他智能合约的 **指令** 的函数。每个指令处理器都会接收输入数据（如账户信息、参数等），执行相应的逻辑，并返回处理结果或对区块链状态进行修改。**instruction**（指令）通常是通过交易（transaction）发送的，交易中包含了指令及其所需的账户信息。当指令到达 Solana 节点时，它们会被发送到对应的程序，并由相应的指令处理器处理。具体来说：
    - **指令（Instruction）**：是一个请求，告诉 Solana 程序执行特定的操作。例如，转账、创建账户、更新数据等。指令可以来自用户、客户端应用或其他程序。
    - **指令处理器（Instruction Handlers）**：是定义在程序中的函数，用于接收和处理这些指令。每个指令处理器会根据指令的类型，检查账户和状态，执行相关逻辑，并在区块链上更新数据。
        - **Instruction Context:** 每个指令处理函数的第一个参数必须是 `Context<T>`。这是 Anchor 框架的一个基本设计模式。`Context<T>` 作为一个容器，封装了程序执行所需的所有非参数（non-argument）输入，其中 `T` 是一个实现了 `Accounts` trait 的结构体，用于指定该指令所需要的账户，这个结构体通过 `#[derive(Accounts)]` 派生宏来表示。
            - `ctx.accounts`: 当前指令所需的所有账户信息。
            - `ctx.program_id`: 当前执行程序的公钥地址。
            - `ctx.remaining_accounts`: 在指令调用中传递，但并未在 `Accounts` 结构体中明确列出的额外账户。客户端可以提供那些没有在 `#[derive(Accounts)]` 中明确指定的账户，这些账户会被捕获到 remaining_accounts 中，供程序进一步处理。
            - `ctx.bumps`: 存储了与 PDA 相关的 **bump seeds**。当你在 `#[derive(Accounts)]` 中定义账户时，可能会涉及到 **Program Derived Address (PDA)** 类型的账户。
        - **可选的附加参数:** 指定在指令调用时必须提供的参数。

- **#[derive(Accounts)]**：应用于结构体，将结构体作为一个指令山下文，用于指定在调用某个指令时必须提供的账户，这里列出的账户必须由客户端提供。结构体中的每个字段表示指令所需的一个账户。
    
    在 Anchor 中，**每个指令**（即智能合约中的每个操作）都必须明确指定哪些账户需要参与该操作。这些账户在 `#[derive(Accounts)]` 派生的结构体中列出，每个字段代表一个特定的账户。这是 Anchor 框架的规定，它旨在确保账户的正确性和安全性。

    💡
    
    Anchor 框架要求你明确列出指令所需的所有账户，并为每个账户定义相关的约束条件（例如是否可写、是否需要签名等）。在原生 Rust 中，也需要处理账户相关的操作，但不需要像 Anchor 这样使用结构体和派生宏来自动管理账户。你需要手动进行账户的验证和数据操作。

    Anchor 会自动为这个 `struct` 实现 `anchor_lang::Accounts` trait。这个 trait 允许 Anchor 运行时在幕后验证和反序列化所有传入指令的账户。它会自动检查账户的公钥、所有权、可写性、签名等，并把这些账户封装成类型安全的 Rust 结构体，供你在程序逻辑中使用。
    
    当指令被调用时，程序会首先验证提供的账户，然后再执行指令的逻辑。验证通过后，可以使用 `ctx.accounts` 语法在指令中访问这些账户。账户验证通常通过两种方式来实现，且这两种方式通常是一起使用的：
    
    - **账户约束 (Account Constraints)**：约束定义了账户必须满足的额外条件，才能被认为是该指令的有效账户。约束是通过 `#[account(..)]` 属性应用的，该属性被放置在实现 `Accounts` 特性的结构体字段上。
    - **账户类型 (Account Types)**：Anchor 提供了各种账户类型，帮助确保客户端提供的账户与程序期望的账户类型匹配。

- **#[account]**：用于标识一个结构体，该结构体将被用来定义程序中自定义账户的数据类型。当你的程序需要创建并管理自定义账户时，可以使用该宏来标记并描述账户的数据结构。
    - 当你定义账户时，Anchor 会自动为这些账户设置 **所有者** 为在 `declare_id!` 宏中指定的程序公钥。这意味着账户的所有权会被自动指向你的程序，确保只有你的程序能修改这些账户的数据。
    - 任何由 Anchor 管理的账户都会包含一个鉴别符。当你定义一个结构体并使用 `#[account]` 属性时，在使用 Anchor 指令创建该结构体的实例（例如使用 `#[account(init)]`）时，Anchor 会自动计算出唯一的8字节鉴别符，并将其写入该账户数据的前8个字节。Anchor 框架以外的方式创建的账户不一定会有这个鉴别符。例如，SPL（Solana Program Library）代币程序管理的账户有自己的头部和数据结构，但它们并没有使用Anchor风格的鉴别符。

    💡
    
    下面两个宏不是同一个宏，功能各不相同。
    
    **#[account(...)]** 是一个属性宏，但它用于修饰 #[derive(Accounts)] 结构体中的字段。它的主要作用是为账户添加约束条件，例如 init、mut、seeds 等，以便在指令执行前进行验证。
    
    **#[account]** 也是一个属性宏，它修饰结构体，定义了账户的数据结构（例如，Poll 账户需要存储哪些字段）。
