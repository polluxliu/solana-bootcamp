# 账户上下文

一笔交易（Transaction）由一个或多个指令（Instruction）组成。每个指令都必须明确列出它需要访问的所有账户。

当你调用 `create_poll` 指令时，你实际上是构建了一个交易，其中包含了这个指令和它要访问的账户列表。当 Solana 运行时处理一个指令时，它会执行以下步骤：

1. **收集账户列表**：从指令中获取所有公钥。
2. **加载账户数据**：
    1. 对于 `Signer` 和 `Program` ，会从区块链状态中读取 `lamports`、`data`、`owner` 等信息。如果不存在，Solana 运行时会立即终止交易。
    2. **对于** `Account` ****，如果账户已存在，它会加载其完整的状态（数据、lamports 等）。如果账户不存在，Solana 运行时会创建一个**临时的、未初始化的账户**。
3. **提供列表**：将加载的账户数据打包成一个列表，然后将其作为参数传递给你的智能合约。

在 `create_poll` 函数体真正开始执行之前，由 `#[derive(Accounts)]` 宏生成的代码会运行。

### `#[derive(Accounts)]`

是 Anchor 框架中一个**过程宏 (procedural macro)**，其为结构体实现了 `Accounts` trait。它的作用是为指令（instruction）自动生成处理和验证账户的样板代码。`Accounts` trait 定义了如何安全地处理一个指令的所有账户。这个 trait 主要有两个核心函数，它们共同完成了**账户验证**、序列化和反序列化的工作。

💡

`#[derive(Accounts)]` 宏中的所有约束都**在指令函数执行之前**被处理。这个过程被称为**账户验证**。

- `from_account_infos` 函数 (账户验证与反序列化)
    
    负责将原始的链上数据，转换成你的程序可以安全、方便使用的 Rust 对象。如果在此过程中任何一个验证失败，它就会返回一个错误，导致交易回滚。
    
    - **接收输入**：它接收 Solana 运行时提供的一个包含所有账户原始信息的列表。
    - **执行验证**：这是所有 `#[account(...)]` 约束被执行的地方。例如，它会检查账户所有权、判别式、是否签名、PDA 地址是否匹配、`init` 约束等。
        
        比如，验证 `poll` 账户是否符合 `init` 约束的要求，即账户是否是**未初始化的**（`lamports` 为 0 且 `data` 为空），如果已经存在（即账户非空），那么 `#[derive(Accounts)]` 宏生成的代码会立即报错，导致整个交易失败。
        
    - **反序列化数据**：如果所有验证都通过，它会将每个账户的原始字节数据 (`data`)，安全地反序列化（deserialize）成你定义的 Rust 结构体，例如 `Poll` 或 `Candidate`。
- `to_account_infos` 函数 (数据序列化)
    
    负责**将你对 Rust 对象的修改，安全地转换回链上存储的格式。**
    
    - **准备输出**：它接收你已经修改过的 Rust 账户对象。
    - **序列化数据**：它将你的 Rust 账户对象重新序列化（serialize）成字节数据，以便写入区块链。
    - **准备跨程序调用 (CPI)**：当你的程序需要调用另一个程序时（例如 `system_program`），`to_account_infos` 也会被调用，以准备好所有账户，并将它们作为参数传递给 CPI。

💡

- **进入 handler 前：**先执行所有约束检查，再对需要的账户做反序列化。
- **进入 handler**：拿到已经校验并解包好的账户对象，写业务逻辑。
- **handler 返回 `Ok(())` 后**：Anchor 自动把被修改的账户重新序列化写回链上。

### `#[instruction()]`

将指令的非账户参数（如 `poll_id`）引入到 `#[Account()]` 宏的作用域，以便在账户约束中使用。

`#[instruction(...)]` 中的参数列表必须和指令函数签名中的参数列表匹配，注意：参数名称**不要求必须和指令函数的参数名称完全一致**，但它们的**顺序和类型必须严格对应**。

### Account Types

- `Account<'a, T>` (数据账户)

`Account` 代表一个由你的程序所拥有的**数据账户**。它是一个包装器，将 Solana 的底层账户数据（`AccountInfo`）与你的自定义数据结构 `T` 关联起来。

- `Signer<'a>` (签名账户)

`Signer` 代表一个在交易中**签名**的账户。签名是授权的证明，任何需要授权的操作都需要 `Signer`。

- `Program<'a, T>` (程序账户)

`Program` 代表一个**程序账户**。它的主要作用是引用另一个程序，以便你的程序可以与其进行跨程序调用（CPI）。当你的程序需要调用另一个程序的功能时，必须将那个程序账户作为参数传入。

**`pub system_program: Program<'a, System>`**：

这是最常见的使用方式。比如，你的 `voting` 程序无法凭空创建账户。它必须通过 CPI 调用 `System Program` 的 `create_account` 指令来完成账户的创建。通过在 `Accounts` 结构中包含 `system_program`，你告诉 Anchor：“嘿，我要调用 `System Program` 来完成一些任务。”

这三个账户类型共同构成了你的程序指令所需的所有信息：

- `Signer` ：**谁**来发起并授权这个操作？
- `Account` ：**哪个账户**的数据将要被读写？
- `Program` ：**哪个程序**将要被调用来辅助完成这个操作？

其他常见的账户类型如下：

- `AccountInfo<'a>` (底层账户信息)
    
    Solana 原生定义的账户类型，用于表示区块链上的任何账户，在 Solana 运行时，所有账户数据都以 AccountInfo 结构体形式存在。Anchor 中的多数高级账户类型都是对它的封装。
    
- `UncheckedAccount<'a>` (不受检查的账户)
    
    告诉 Anchor：**不要对这个账户做任何验证或转换（对其 `data` 字段反序列化 / 序列化），只把原始数据交给我**。使用时，必须添加一条以 `///CHECK:` 开头的文档注释，解释为何这里不需要验证或转换。注意，你仍然可以在 `#[account(...)]` 里写声明式约束，这些显式约束会在进入 handler 前被执行。如果你什么约束都不写，它就真的不检查。
    
- `SystemAccount<'a>` (系统账户)
    
    这是一个**钱包账户**：
    
    - 账户已初始化
    - `data` 字段为空
    - `owner` 为系统程序 (`owner = system_program::id()`)

    💡 广义上，system program 管理的账户，还可以有别的用途，并不是所有 system program 创建的账户都一定是 `SystemAccount<'a>`。如果你用 system program 创建了一个账户，并分配了 `space > 0`，但还没把它的 owner 改成别的程序，这种账户就不能用 `SystemAccount<'a>` 声明，只能用 `UncheckedAccount<'a>` 或 `AccountInfo<'a>` 来接收。

- `Sysvar<'a, T>` (系统变量账户)
    
    表示一个由 Solana 内置提供的只读 **系统变量账户**，比如：
    
    - `Sysvar<'a, Rent>` 租金信息
    - `Sysvar<'a, Clock>` 当前 slot、时间戳
    - `Sysvar<'a, RecentBlockhashes>` 历史区块哈希
    
    这些账户无法被修改，只能读。
