# 6 - 交易元数据

当一个交易执行时，Solana runtime 会记录它的执行过程，写入到 transaction logs 中。

在某个 slot 内，被选中的 **leader** 节点负责打包交易，它会执行交易，然后把新的区块广播给其他 validator。当其他 validator 收到 leader 的区块时，它们也会对交易进行 replay（重放执行）。所有 validator （包括 RPC 节点或 Archival 节点）最终都会执行一遍交易，leader 和 validator 在执行时都会生成一份日志，这些日志存储在本地数据库里。

你在本地跑 `anchor test` 或在区块浏览器里看某个交易的日志，里面都能看到 `msg!` 打印的内容。因为这些日志属于交易元数据的一部分，客户端和区块浏览器都能读取。

交易日志是 **交易元数据 (transaction meta)** 里的一部分。交易元数据是 Solana 交易执行后，节点生成的关于该交易的执行结果和统计信息。你可以把交易元数据想象成一个交易的收据或报告。它主要包括以下信息：

- 执行状态 (Execution Status): 这条交易是成功了还是失败了？如果失败了，是什么原因？这是客户端最关心的信息之一。
- 日志消息 (Log Messages): 这是程序执行过程中通过 `msg!` 或 `event!` 宏打印出来的所有信息。
- 计算单元 (Compute Units) 使用情况: 交易执行实际消耗了多少计算单元？这是了解交易性能和优化程序效率的关键指标。
- 费用 (Fee): 这条交易实际支付了多少 SOL 的交易费用？
- 账户锁 (Account Locks): 交易在执行过程中锁定了哪些账户？这对于理解交易的并发性非常重要。
- 预执行和后执行账户状态 (Pre- and Post-Balances): 交易执行前后，所有受影响账户的 SOL 余额变化。这对于审计和验证交易的正确性非常有用。

💡

当一个客户端（比如钱包或 DApp）发送一笔交易时，它只提供了 **要做什么**。而当这笔交易被验证器执行后，验证器会生成一份完整的交易元数据，这份数据回答了 **发生了什么**。

客户端可通过 RPC 查询这笔交易。`getTransaction` 是一个 RPC 接口，用来查询 **单笔交易的详细执行结果**，根据交易的 **signature**，查询该笔交易的完整元数据，返回的是该 RPC 节点 **本地保存的执行日志**。可以通过 Solana CLI 来调用这个接口，指令 `solana transaction <signature>` 的底层就是调用了这个接口。

另外也可使用 `solana logs` 指令，其用于实时订阅并打印交易执行时的日志输出。这个指令会连接到一个 RPC 节点，订阅 `logsSubscribe` WebSocket API。默认会连接到你配置的集群（`solana config get` 查看）。

- 指定关注的程序：

```bash
solana logs | grep <PROGRAM_ID>
```

- 指定 RPC 节点：

```bash
solana logs --url https://api.devnet.solana.com
```

注意，交易元数据的存储通常是有时间限制的，大多数 RPC 节点不会无限期存储交易历史，与 RPC 节点相比，Validator 节点对交易元数据的保留期更短。
