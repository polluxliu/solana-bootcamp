# 7 - 交易从创建到广播

## **交易创建**

在钱包里创建一个 Solana 交易，生成原始的数据，里面包含要执行的指令、需要用到的账户地址和对交易的签名。

## 交易提交

钱包会将这笔签名后的交易序列化成二进制数据，通过 **JSON-RPC over HTTPS** 协议发送给一个 RPC 节点。这里的 JSON-RPC over HTTPS 指的是用 HTTPS 协议传输 JSON-RPC 格式的请求与响应。JSON-RPC 是一种 **轻量级的远程调用协议**，定义了请求和响应的结构。其请求格式为：

```json
{
  "jsonrpc": "2.0",
  "method": "subtract",
  "params": [42, 23],
  "id": 1
}
```

- `jsonrpc`: 指定版本号（2.0）
- `method`: 远程要调用的方法名
- `params`: 调用参数（可以是数组或对象）
- `id`: 请求的唯一标识，用于匹配响应

其响应格式为：

```json
{
  "jsonrpc": "2.0",
  "result": 19,
  "id": 1
}
```

- `result`: 方法返回的结果
- `id`: 与请求中的 `id` 匹配，确保一一对应

如果出错，会返回：

```json
{
  "jsonrpc": "2.0",
  "error": {
    "code": -32602,
    "message": "Invalid params"
  },
  "id": 1
}
```

## 交易广播

当 RPC 节点收到一个合法的交易请求时，它会立即通过 Gulf Stream 协议把这笔交易定向广播给当前和未来的区块领导者。

- 当前的区块领导者（current leader）
- 以及接下来几个时隙（slot）的未来领导者（upcoming leaders）

下面我们从互联网协议栈的视角看一下交易是如何被广播的。互联网协议栈的典型分层如下：

- 应用层：HTTPS (HTTP + TLS/SSL), FTP, DNS, Gossip, Gulf Stream
    
    应用层负责 **为用户和应用程序提供网络服务和接口**，实现各种网络服务和应用功能，确保用户数据能够被正确发送和接收，是用户体验网络的直接层。
    
- 传输层：TCP / UDP
    
    传输层负责从源主机到目的主机的 **端到端的传输控制**，为应用层提供可靠或非可靠的数据传输服务。为两个主机上的应用程序之间提供逻辑上的端到端通信，保证数据能够可靠、有序地传送。数据单位是段。
    
- 网络层：IP (IPv4 / IPv6)
    
    网络层负责实现从源主机到目的主机的 **端到端的数据包路由与转发**，确保数据包能通过多个中间网络节点（如路由器）找到合适路径到达目的地。数据单位是包。
    
- 链路层：Ethernet / Wi-Fi
    
    链路层负责 **在两个直接相连节点之间的链路上，完成数据的封装和传输**。链路是指两个直接相连的设备之间的一段物理或逻辑连接，可以是点对点的、也可以是多点广播的链路。数据单位是帧。
    
- 物理层：光纤 / 电缆 / 无线信号

同 Gossip 协议一样，Gulf Stream 协议也是应用层协议（其定义了交易转发的逻辑和策略），在传输层使用的也是 **UDP**（User Datagram Protocol）协议。UDP 会把从应用层接收到的 JSON-PRC 数据作为 **Payload** 放入 **报文（Datagram）中**。一个完整的 UDP 报文 (UDP Datagram) = **UDP Header (8 字节) + 应用层数据 (payload)**。

```json
[ UDP Header ][ JSON-RPC 数据 ]
```

除了 Payload，UDP 报文中添加了一个 **UDP Header（8 字节）**，里面包含：

- 源端口号 (Source Port)：表示发送方应用进程的端口号
- 目标端口号 (Destination Port)：表示接收方应用进程的端口号
- 长度 (Length)：包含整个 UDP 报文的字节数（Header + Payload）
- 校验和 (Checksum)：用来验证数据在传输过程中是否被篡改或损坏

接着 UDP 的数据报文会被交给网络层，整个数据报文会作为一个 **Payload**，由 **IP** 协议再包裹一层新的 Header，得到一个 **包（Packet）**。网络层的 IP 协议分为 IPv4 和 Ipv6 两种版本，它们的 Header 是不同的：

- IPv4 Header（最小 20 字节，可变长）
- IPv6 Header（固定 40 字节）

```json
[ IP Header ][ UDP Header ][ JSON-RPC 数据 ]
```

IP Header 的主要内容：

- **Version**
    - IPv4：Version = 4
    - IPv6：Version = 6
    - 用来表明使用的 IP 协议版本。
- **源地址 (Source Address)**
    - IPv4：32 位地址（4 字节）
    - IPv6：128 位地址（16 字节）
    - 表示发送方的 IP 地址。
- **目标地址 (Destination Address)**
    - IPv4：32 位地址
    - IPv6：128 位地址
    - 表示接收方的 IP 地址。

接着 IP 的包会被交给链路层，这一层负责在单个物理网络段上传输数据。它会将 IP 包封装一个 **帧（Frame）**中，并在前后添加头部和尾部，尾部通常是帧校验序列 FCS，例如以太网中的 CRC32。

不同的物理介质（光纤、铜线、无线电波）和使用场景（局域网、广域网、移动网络等），有不同的链路层协议。**不同链路层协议有各自不同的帧格式，**在帧头 / 帧尾里的字段和内容不一样。比如以太网（Ethernet）的帧格式如下：

```json
[ Ethernet Header ][ IP Header ][ UDP Header ][ JSON-RPC 数据 ][ CRC ]
```

其中 Ethernet Header 的主要内容（14 字节）：

- Destination MAC Address（目标 MAC 地址，6 字节）
    - 表示该帧要发送到的设备的物理地址。
    - 网络中的每个网卡（NIC, Network Interface Card）都有唯一的 MAC 地址（48 bit，一般写成 6 组十六进制数）。
    - 如果目标是广播，就会用 `FF:FF:FF:FF:FF:FF`。
- Source MAC Address（源 MAC 地址，6 字节）
    - 表示该帧的发送方设备的物理地址（即网卡的硬件地址）。
    - 让接收方知道是谁发来的，可以用于响应。

最终，在物理层，将链路层的帧转化为物理信号进行传输。信号的物理形式：

- **电信号**：有线以太网（铜线） → 电压高低代表 0 和 1。
- **光信号**：光纤 → 光的脉冲（有光/无光，或不同波长）。
- **无线信号**：Wi-Fi / 5G → 电磁波（频率、相位、幅度变化表示 0 和 1）。

不同的物理媒介如以太网、光纤、无线等具有不同的传输特性，诸如信号传播方式、带宽、干扰抗性、误码率等，这些物理特性**直接影响链路层能够传输的单个帧的大小**。而各链路层协议的最大帧长不同，网络层就需要一个统一的最大数据包长度限制（MTU）来适应各种不同链路的差异，保证数据包能在不同链路之间传输。**Maximum Transmission Unit（最大传输单元）**指在一次网络传输中，网络层的一个数据包（Packet）能携带的 **最大字节数**。如果数据超过 MTU，就需要拆分成多个包发送，网络层会把一个大 IP Packet 拆成多个小的 IP Packet。

IPv4 规定的最小 MTU 为 576 字节，IPv6 协议规定了 1280 字节为强制支持的最小 MTU，也就是说，在任何网络环境里，**都能保证至少能发 1280 字节的 IP 包**。Solana 基于 IPv6 的规范对交易大小进行了限制。在 IPv6 下：

- MTU = 1280
- IPv6 头 = 40 字节
- UDP 头 = 8 字节

从而可用的载荷为：

$$
 payload = 1280 - 40 - 8 = 1232 字节
$$

这就是为什么 Solana 中 **单笔交易大小限制在 1232 字节**。
